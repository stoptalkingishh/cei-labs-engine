# P1 Fix Log — 2026-07-23

Branch: `fix/p1-image-pinning` (worktree `/opt/cei-labs/wt-image-pinning`, base
commit `8308661`). Covers the two P1 items in
`CEI-Labs-Wargames-Fix-Notes.md`'s "Stable access endpoint and image

## Investigation

### Reality check on the "images live in a real registry" assumption

The task brief said `docker manifest inspect` against
`ghcr.io/stoptalkingishh/...` had earlier returned "denied," implying no
real registry is in play. Re-checked live on this station and that is only
partly true:

- `docker manifest inspect ghcr.io/stoptalkingishh/cei-labs-engine/ctf-kali-novnc:latest`
  **succeeds** anonymously and returns a real multi-platform manifest index
  — `ctf-kali-novnc:latest` genuinely is built and pushed to GHCR by
  `.github/workflows/build-kali-novnc.yml` on every push to `main`.
- But the manifest digest GHCR currently serves for `:latest`
  (`sha256:1a35d5e3...`) does **not** match this station's locally-tagged
  `ctf-kali-novnc:latest` image ID (`sha256:4d3d7531...`) — the local tag
  is a snapshot from an earlier CI push and has since drifted from what
  the mutable tag now points to upstream. That drift is the exact risk
  category this task exists to close.
- `:offline`-tagged images (`ctf-kali-novnc:offline`, `tcp-gateway:offline`)
  are **not** in GHCR at all (`manifest unknown`) — those are genuinely
  local-only builds from the offline/air-gapped installer path (matches
  the "Add fully offline installer for air-gapped Fedora deployment" repo
  history).
- Docker Engine here is 29.6.2 with the containerd (`io.containerd.snapshotter.v1`)
  image store, which is why even the local-only `:offline` builds already
  carry real `RepoDigests` entries without ever being pushed — that
  storage backend computes/records manifest digests for local content, not
  only pulled/pushed content. This is what makes local-digest pinning
  viable at all in this deployment model.

**Conclusion:** this deployment mixes both realities per-image — some tags
really do round-trip through GHCR, others exist only locally — and either
way, the actual risk to close per the bug report ("stuck in `Preparing`
when it referenced an unavailable remote image tag") is that a *fresh*
Swarm task resolving a mutable `:latest` reference can require a registry
round-trip that this deployment cannot depend on succeeding (private
package auth, drifted tag, or a genuinely offline node). Pure textbook
"pin to the GHCR digest" doesn't reliably fix that here, because the GHCR
digest for `:latest` can itself be different from what was tested/loaded
onto this station's nodes.

### The actual fix implemented

`docker/orchestrator/app/docker_client.py`: `DockerOrchestratorClient.create_service`
now resolves every service's image reference to the digest already present
in the **local** image store (`docker image inspect`'s `RepoDigests`,
via docker-py) before calling the Swarm API — `repo:latest` becomes
`repo@sha256:...`. This:

- Removes the registry round-trip for task placement entirely when the
  digest is already cached (the common case in this offline-build model),
  which is what actually prevents the `Preparing`-stuck failure mode.
- Also closes the more conventional "mutable tag reassigned after testing"
  risk, the same way `docker/stack.yml` already pins traefik/mariadb/redis
  by digest.
- Applies uniformly to every image the orchestrator deploys (attacker
  `ctf-kali-novnc`, `tcp-gateway`, and challenge target images), not just
  the two called out in the brief — same mechanism, same fallback, no
  reason to special-case.
- Falls back to the original tag reference, unresolved, with a logged
  warning, if the image isn't present locally at all (e.g. a fresh dev
  box relying on a real registry pull) — documented as the one case this
  can't protect against, per the brief's "as a documented fallback"
  guidance.

Not implemented: an explicit `@sha256:...` literal baked into
`instance_types.py`'s `GATEWAY_IMAGE` default or the CTFd
`attacker_image`/`target_image` admin config strings. Those stay mutable
tags by design (they're admin/operator-configured, rebuilt locally, no
fixed "release" digest exists for them the way `traefik:v3.7.6` has one) —
resolution happens at deploy time instead, against whatever is actually
loaded on this station right now, which is the only digest that's
meaningful for a locally-built image.

Tests: `docker/orchestrator/tests/test_docker_client.py` — new coverage for
`resolve_image_digest` (pins to a matching local `RepoDigests` entry,
ignores a digest for a different repo, falls back when no digest is
recorded, falls back when the image isn't present locally at all) and for
`create_service` actually using the resolved reference in both the
success and fallback cases.

### Stable access endpoint

`docker/orchestrator/app/config.py`'s `Config.BASE_DOMAIN` was **already**
environment-driven (`ctf.local` default, no IP anywhere) — this was never
a code bug. The `192.168.1.131` incident was a station IP copied into
player-facing launch instructions (a separate repo/artifact, out of scope
for this worktree) that was never revisited after the station's address
changed.

Fix is documentation, matching the brief's own framing:

- `docker/.env.example`: added an explicit warning next to `BASE_DOMAIN`
  against copying a point-in-time station IP into launch instructions,
  pointing at the incident and at the new runbook section.
- `docs/network-prerequisites.md`: new "Stable access endpoint" section —
  explains the failure, states this repo never hardcodes an IP, documents
  this station's **current** confirmed value (`192.168.1.173`, verified
  live 2026-07-23) with an explicit "this will go stale too, re-verify
  before relying on it" caveat, and restates the pre-event acceptance
  check from the fix notes (clean-client DNS/hostname reachability test
  for CTFd/SSH/noVNC).
- `docker/orchestrator/tests/test_config.py`: new regression test —
  asserts `Config.BASE_DOMAIN`'s default is never a bare IPv4 literal, and
  that it's still overridable via env. Guards against a future "fix" that
  reintroduces the same failure mode by hardcoding a station IP as the
  default.

## Open question for review

The digest-pinning fix assumes every Swarm node that could schedule an
attacker/target/gateway task has loaded *identical* image content (same
digest) via the offline installer. That's true for this station's current
single-node deployment, but if this cluster grows to multiple nodes, a
node whose local build/load produced a different digest for the same
logical image (e.g. rebuilt at a different time) would fail to resolve
the pinned digest and the task would fail to start — loudly, at least,
rather than hanging in `Preparing`, but still worth a human call on
whether that tradeoff (fail-fast-but-node-specific vs. fall through to a
registry pull) is the right one for a real multi-node event, and whether
the offline installer should be extended to verify/record a shared digest
manifest across nodes as part of setup.

# P1 Fix Log — Kali noVNC "Web Browser" launcher has no browser

Branch: `fix/p1-browser-launcher` (worktree `/opt/cei-labs/wt-browser-launcher`, base `8308661`)

## Bug

`operator/kali-novnc/Dockerfile` installed no browser at all. The desktop's
"Web Browser" launcher icon (`xfce4-web-browser.desktop`) runs
`exo-open --launch WebBrowser %u`, which had nothing to resolve to:
`command -v firefox chromium google-chrome` all failed and
`update-alternatives --list x-www-browser` errored `no alternatives` on the
live `chrange-1`-network attacker container. That container has no internet
access (isolated overlay network, by design, for tenant isolation), so this
had to be fixed at image build time, not patched live.

## Investigation: how `exo-open --launch WebBrowser` actually resolves

Traced live inside a throwaway container built from the (pre-fix) image:

1. `xfce4-web-browser.desktop`'s `Exec=exo-open --launch WebBrowser %u`
2. exo reads `/etc/xdg/xfce4/helpers.rc`: `WebBrowser=debian-sensible-browser`
   (this is the Debian/Kali default, unmodified by this image)
3. `debian-sensible-browser.desktop` -> `X-XFCE-Binaries=sensible-browser`
4. `/usr/bin/sensible-browser` (from `sensible-utils`) tries, in order:
   `$BROWSER`, then — since the noVNC desktop session always has `$DISPLAY`
   set — `x-www-browser`; it only falls back to plain `www-browser` when
   `$DISPLAY` is *unset* (e.g. a bare SSH/no-desktop session)

So the launcher icon's actual dependency is `x-www-browser` resolving via
`update-alternatives`, not literally a binary named `www-browser`.

Installed `chromium` (Debian package, not `chromium-browser` — that's the
current name in Kali-rolling's repos as of this fix) in a scratch container
and confirmed:

- Binary lands at `/usr/bin/chromium` (307MB installed, pulls the expected
  GTK3/X11 dependency chain, no surprises)
- The package's own postinst **already** runs
  `update-alternatives --install .../x-www-browser x-www-browser /usr/bin/chromium ...`
  automatically — verified live: `update-alternatives --list x-www-browser`
  reports `/usr/bin/chromium` immediately after `apt-get install chromium`,
  with zero manual steps. So the actual exo-open path (`$DISPLAY` set) works
  from the `chromium` package alone.
- `chromium` does **not** register a `www-browser` alternative/binary (only
  a dpkg `Provides: www-browser` virtual-package tag, which is not a binary
  on `PATH`) — confirmed live: `command -v www-browser` fails after
  installing chromium with nothing else. This matters for (a) the
  `$DISPLAY`-unset sensible-browser fallback and (b) this project's stated
  fix convention of a `/usr/local/bin/www-browser` compat shim, so it's
  added explicitly rather than assumed.

## Fix

`operator/kali-novnc/Dockerfile`:
- Added `chromium` to the main `apt-get install` package list.
- Added a follow-up `RUN` step that verifies `chromium` is on `PATH`,
  verifies `update-alternatives --list x-www-browser` already resolves
  (fails the build loudly if a future Kali/Debian packaging change ever
  drops that automatic registration), symlinks
  `/usr/local/bin/www-browser -> /usr/bin/chromium`, and verifies that
  shim resolves too.
