# P1 Fix Log — Kali noVNC "Web Browser" launcher has no browser

Branch: `fix/p1-browser-launcher` (worktree `/opt/cei-labs/wt-browser-launcher`, base `8308661`)

## Bug

`operator/kali-novnc/Dockerfile` installed no browser at all. The desktop's
"Web Browser" launcher icon (`xfce4-web-browser.desktop`) runs
`exo-open --launch WebBrowser %u`, which had nothing to resolve to:
`command -v firefox chromium google-chrome` all failed and
`update-alternatives --list x-www-browser` errored `no alternatives` on the
live `chrange-1`-network attacker container. That container has no internet
access (isolated overlay network, by design, for tenant isolation), so this
had to be fixed at image build time, not patched live.

## Investigation: how `exo-open --launch WebBrowser` actually resolves

Traced live inside a throwaway container built from the (pre-fix) image:

1. `xfce4-web-browser.desktop`'s `Exec=exo-open --launch WebBrowser %u`
2. exo reads `/etc/xdg/xfce4/helpers.rc`: `WebBrowser=debian-sensible-browser`
   (this is the Debian/Kali default, unmodified by this image)
3. `debian-sensible-browser.desktop` -> `X-XFCE-Binaries=sensible-browser`
4. `/usr/bin/sensible-browser` (from `sensible-utils`) tries, in order:
   `$BROWSER`, then — since the noVNC desktop session always has `$DISPLAY`
   set — `x-www-browser`; it only falls back to plain `www-browser` when
   `$DISPLAY` is *unset* (e.g. a bare SSH/no-desktop session)

So the launcher icon's actual dependency is `x-www-browser` resolving via
`update-alternatives`, not literally a binary named `www-browser`.

Installed `chromium` (Debian package, not `chromium-browser` — that's the
current name in Kali-rolling's repos as of this fix) in a scratch container
and confirmed:

- Binary lands at `/usr/bin/chromium` (307MB installed, pulls the expected
  GTK3/X11 dependency chain, no surprises)
- The package's own postinst **already** runs
  `update-alternatives --install .../x-www-browser x-www-browser /usr/bin/chromium ...`
  automatically — verified live: `update-alternatives --list x-www-browser`
  reports `/usr/bin/chromium` immediately after `apt-get install chromium`,
  with zero manual steps. So the actual exo-open path (`$DISPLAY` set) works
  from the `chromium` package alone.
- `chromium` does **not** register a `www-browser` alternative/binary (only
  a dpkg `Provides: www-browser` virtual-package tag, which is not a binary
  on `PATH`) — confirmed live: `command -v www-browser` fails after
  installing chromium with nothing else. This matters for (a) the
  `$DISPLAY`-unset sensible-browser fallback and (b) this project's stated
  fix convention of a `/usr/local/bin/www-browser` compat shim, so it's
  added explicitly rather than assumed.

## Fix

`operator/kali-novnc/Dockerfile`:
- Added `chromium` to the main `apt-get install` package list.
- Added a follow-up `RUN` step that verifies `chromium` is on `PATH`,
  verifies `update-alternatives --list x-www-browser` already resolves
  (fails the build loudly if a future Kali/Debian packaging change ever
  drops that automatic registration), symlinks
  `/usr/local/bin/www-browser -> /usr/bin/chromium`, and verifies that
  shim resolves too.

## Verification

Image build completed (`ghcr.io/stoptalkingishh/cei-labs-engine/ctf-kali-novnc:latest`,
image ID `199d0f8b214c`, built 2026-07-23 07:30:22 -0400, ~8 min after the
Dockerfile commit `c8a97cf`). Ran a fresh throwaway container from that
image and captured actual output:

```
$ docker run --rm ghcr.io/stoptalkingishh/cei-labs-engine/ctf-kali-novnc:latest \
    bash -c 'echo "chromium: $(command -v chromium)"; \
             echo "www-browser: $(command -v www-browser)"; \
             echo "x-www-browser alt: $(update-alternatives --list x-www-browser)"'
chromium: /usr/bin/chromium
www-browser: /usr/local/bin/www-browser
x-www-browser alt: /usr/bin/chromium
```

`/usr/local/bin/www-browser` confirmed as a symlink to `/usr/bin/chromium`
(`lrwxrwxrwx ... www-browser -> /usr/bin/chromium`), and it is the genuine
Chromium launcher script (verified by reading the shim target's contents,
not just its presence).

`cei-labs_ctfd`, `cei-labs_ctfd-db`, `cei-labs_ctfd-redis`,
`cei-labs_orchestrator`, `cei-labs_traefik` — no `chrange-*`/`chinst-*`

`ctf-kali-novnc:latest` image will be picked up automatically by any
freshly-provisioned attacker instance; `docker service update --force
<name>` remains the correct action for any existing attacker service the
next time one is live and needs to pick up this fix without a full
redeploy. CTFd/DB/Redis/Traefik/orchestrator and the unrelated
`open-terminal`/`open-webui`/`portainer` containers were not touched.
