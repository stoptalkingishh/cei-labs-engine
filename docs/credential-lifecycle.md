# Credential lifecycle

Which orchestrator operations rotate a team's flags and level passwords, and
which ones preserve them.

This document exists because getting it wrong is silent. Rotating a team's
secrets does not fail loudly, does not appear in CTFd, and does not touch the
`solves` table — so the scoreboard keeps showing the progress a player earned
while the environment behind it no longer accepts any password they wrote
down. See "Incident: 2026-08-06" below.

## What a "credential" is here

Two separate families, both generated by the orchestrator and both covered by
the vault:

- **Per-team level secrets** — one random value per level key
  (`bandit0`..`bandit33`, `krypton1`..`krypton6`, `natas0`..) generated by
  `instance_types.generate_track_secrets()` and its `_alpha` / `_fixed`
  variants. Injected into the target container as the `LEVEL_SECRETS` JSON
  blob, which the image's `entrypoint.sh` turns into actual account passwords
  and file contents. Also persisted CTFd-side into
  `instance_launcher_team_secrets`, which is what `PerTeamDynamicFlag.compare()`
  validates submissions against.
- **Per-team attacker credentials** — the shared range workstation's
  `ssh_password` / `novnc_password`, generated in
  `instance_types.plan_range_attacker()`.

Both are *derived state*: the target images hold no baked-in passwords, so
whatever the orchestrator generates on a given launch is the full truth for
that environment.

## The rule

> A team's secrets change **only** when that team explicitly asks for a reset.
> Nothing automatic — no timeout, no idle sweep, no resource reclamation, no
> restart — may ever change them.

## Operation matrix

| Operation | Trigger | Container | Secrets |
|---|---|---|---|
| `pause()` / `pause_range()` | idle grace elapsed; post-solve shutdown countdown | removed | **preserved** (store row kept) |
| resume | next `create_or_get()` touch | recreated | **preserved** |
| `teardown()` / `teardown_range()` | absolute-lifetime reap; admin delete | removed | **preserved via vault** |
| orchestrator restart / stack redeploy | operator | unchanged or recreated | **preserved via vault** |
| `create_or_get(force_relaunch=True)` | player clicks **Relaunch Environment** | destroyed + recreated | **rotated** |

`force_relaunch=True` is the one row that rotates, and it is the only one that
calls `purge_vaulted_secrets()`. That call sits in `controller.create_or_get()`
inside the `if replacement_record is not None:` branch, which is reachable
*only* from the explicit relaunch path — the reaper's `teardown()` never
enters it.

## The vault

`InstanceStore.instance_secret_vault` (keyed by `owner_id`, `instance_key`) and
`RangeStore.range_secret_vault` (keyed by `owner_id`) are deliberately
**outside** the `instances` / `ranges` tables, and outlive their rows.

That separation is the whole mechanism. A `teardown()` deletes the `instances`
row so the next `create_or_get()` builds a genuinely fresh plan — new port, new
service name, new container. The vault row survives that, so the *plan* is new
while the *secrets inside it* are the team's originals.

Read side, in `plan_single_target()` / `plan_range_target()`:

```python
track_secrets.update({k: v for k, v in existing_secrets.items() if k in track_secrets})
```

Vaulted values overwrite freshly-generated ones key-for-key. The `if k in
track_secrets` guard means a level added to the track since the team last
launched still gets a fresh value — the vault restores, it never constrains
which keys exist.

Write side, `controller._vault_track_secrets()`, called after every successful
create. `merge_vaulted_secrets()` is merge-not-overwrite (`{**secrets,
**existing}` — existing wins), so re-vaulting an already-vaulted key is a no-op
and there is no way for a later launch to clobber an earlier value.

Both vaults are encrypted at rest with the same `credential_encryption_key`
Fernet key as `plan_json` (see `crypto.py`). **If that secret is lost or
rotated, every vaulted secret becomes unrecoverable** — `get_vaulted_secrets()`
will raise on the `json.loads()` of a failed decrypt rather than silently
handing back garbage. Back it up with the rest of `docker/secrets/`.

## Operator guidance

- `ORCHESTRATOR_MAX_INSTANCE_LIFETIME_MINUTES` is measured from `created_at`,
  not `last_accessed` — it tears down teams who are actively playing. Set it
  longer than any single event runs. Use `ORCHESTRATOR_IDLE_GRACE_MINUTES`
  (non-destructive pause) to reclaim resources from inactive teams instead.
- Back up `docker/secrets/credential_encryption_key.txt` alongside the
  `orchestrator_data` volume. Either one alone is useless.
- After changing orchestrator code, confirm the running image actually has it:
  ```
  docker exec $(docker ps -q -f name=cei-labs_orchestrator) \
    grep -c instance_secret_vault /app/app/store.py
  ```
  A `0` means the deployed image predates the vault, whatever `git log` says.

## Incident: 2026-08-06

Players reported that their wargame accounts stopped working after an
environment relaunch, while their CTFd scores still showed correctly.

The vault described above existed as **uncommitted working-tree changes** on
the lab station and had never been committed, pushed, built, or deployed. The
running orchestrator image contained none of it (`grep -c
instance_secret_vault /app/app/store.py` → `0`; `state.db` had no vault
tables). Several merged PRs had made level *content* deterministic given a
stable `LEVEL_SECRETS` — Wargames #45 derived the bandit13→14 SSH keypair from
`bandit13`'s own secret, #44 did the same for Krypton's keystream, engine #48
made `plan_range_target()` consume `secret_keys` at all — which made the
problem look addressed. None of them made `LEVEL_SECRETS` itself stable across
a teardown; only the vault does that.

With `ORCHESTRATOR_MAX_INSTANCE_LIFETIME_MINUTES=240`, every team's box was
destructively reaped 4 hours after creation and re-created with entirely new
passwords. CTFd's `_persist_and_scrub_secrets()` then overwrote
`instance_launcher_team_secrets` with the new values, so flag validation stayed
self-consistent and nothing errored — while every password a player had
written down became dead. `solves` was never touched, which is why scores
looked fine and masked the failure for as long as they did.

The pre-rotation secrets were not recoverable: they had never been persisted
anywhere, which is precisely the bug. Affected players were instead issued
their *current* passwords for levels they had already solved, letting them
resume at their high-water mark.
