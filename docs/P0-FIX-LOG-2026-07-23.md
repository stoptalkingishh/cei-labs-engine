# P0 fix log: VNC/SSH attacker-workstation password truncation

## 2026-07-23 -- fix/p0-vnc-ssh-password

### The bug

`plan_range_attacker()` in `docker/orchestrator/app/instance_types.py`
generated ONE `secrets.token_urlsafe(18)` string (20+ characters) and set
both `VNC_PASSWORD` and `OPERATOR_PASSWORD` to that same value. The
attacker workstation's launch panel then surfaced a single
`attacker_password` field, presented as "the" password for both SSH and
noVNC.

TigerVNC's protocol silently truncates its password to 8 characters --
`vncpasswd -f` does not warn or error, it just discards everything past
the 8th byte. So SSH (via `chpasswd`, no length limit) honored the full
generated string, while VNC only ever actually accepted its first 8
characters. Whatever the UI displayed as "the" password would silently
fail to authenticate over noVNC unless a player happened to truncate it
themselves.

Separately, on inspection `operator/kali-novnc/Dockerfile`'s embedded
`/start.sh` turned out to not even reference `OPERATOR_PASSWORD` at all --
it read `VNC_PASSWORD` for *both* `chpasswd` (the Linux/SSH account) and
`vncpasswd -f` (VNC auth). `OPERATOR_PASSWORD` was dead weight for this
image (it's meaningful only for `operator/analyst/Dockerfile`, the
SSH-only variant with no VNC server at all). So the two orchestrator env
vars were not actually independent inputs into two different mechanisms
for kali-novnc -- both were driven off one value under the hood too.

### The fix

1. **`docker/orchestrator/app/instance_types.py`** (`plan_range_attacker`):
   generate two genuinely separate values --
   - `ssh_password = secrets.token_urlsafe(18)` (unchanged, long/high-entropy, no truncation ceiling to worry about for SSH/chpasswd)
   - `novnc_password` = a fresh 8-character alphanumeric string (`secrets.choice` over `string.ascii_letters + string.digits`), generated at exactly the length TigerVNC actually honors so there is no truncation gap between what's generated and what's usable.
   - `attacker_env["OPERATOR_PASSWORD"] = ssh_password`, `attacker_env["VNC_PASSWORD"] = novnc_password`.
   - `access` dict: replaced the single `attacker_password` key with two clearly labeled fields, `ssh_password` and `novnc_password`. No shared/merged `password` field remains anywhere in the response.

2. **`operator/kali-novnc/Dockerfile`** (`/start.sh`, generated inline):
   - now checks both `OPERATOR_PASSWORD` and `VNC_PASSWORD` are set at container start (fails loudly, refuses to start with no password, same as before -- just for both vars now).
   - `chpasswd` now uses `OPERATOR_PASSWORD` (was `VNC_PASSWORD`).
   - `vncpasswd -f` continues to use `VNC_PASSWORD` (unchanged target, now genuinely a different value than what drives SSH).
   - Updated the Dockerfile-level comments (the "VNC_PASSWORD is intentionally not an ARG" block, the "same account, same password" line, the `/start.sh` comment) to describe the two-credential model instead of implying a single shared secret.

3. **Launch-panel surfaces** -- grepped `docker/orchestrator/app/` and the CTFd instance-launcher plugin broadly for `attacker_password` / `VNC_PASSWORD` / `OPERATOR_PASSWORD`; the only two places that rendered the old shared field to end users were:
   - `docker/ctfd/plugins/instance-launcher/assets/challenge-launch.js` (the in-modal JS panel)
   - `docker/ctfd/plugins/instance-launcher/templates/instance_launcher/launch.html` (the no-JS fallback page)

   Both now render three distinct lines -- Username, "SSH / console password", "noVNC password" -- instead of one combined "Login: user / password" line captioned "needed for both noVNC and SSH" (which was actively misleading given the bug above).

   `operator/analyst/Dockerfile` (the SSH-only, no-VNC image) was already correctly using only `OPERATOR_PASSWORD` and needed no change -- confirmed by reading it, not assumed.

## Bug

`VNC_PASSWORD`/`OPERATOR_PASSWORD` (and single-target/wargame level flags baked
into `env`) were generated fresh — via `instance_types.plan_*()`, which calls
`secrets.token_urlsafe()`/`generate_track_secrets()` — every time a *new*
`InstanceRecord`/`RangeRecord` row was created. That's correct for an actual
first launch or an explicit relaunch. The bug: the idle reaper and the
post-solve shutdown countdown both went through `InstanceController.teardown()`/
`teardown_range()` — the same *destructive* path used for an explicit delete —
which deletes the store row entirely. The next time a learner reopened the
challenge (an ordinary, non-`relaunch` `POST /instances` call), `create_or_get()`
found no existing row, replanned from scratch, and silently handed back a
*new* set of credentials under the same `status="exists"`-shaped response the
learner had no reason to distrust.

Docker/Swarm-level restarts (host reboot recreating a task, `force_update()`
in `reboot()`) were never actually the bug — a service's env is part of its
task spec and survives those untouched. The real gap was idle/shutdown-driven
*teardown*, not restart.

## Fix

Introduced a non-destructive "pause" state, orthogonal to teardown:

- `InstanceRecord.stopped` / `RangeRecord.stopped` (new `stopped` column,
  `docker/orchestrator/app/store.py`, migrated onto the existing on-disk db
  via `ALTER TABLE ... ADD COLUMN` guarded against "duplicate column").
- `InstanceController.pause()` / `pause_range()` (`controller.py`): remove the
  live Docker service(s) (and, for a single/web-app instance, its own
  network) but **keep the store row** — same `plan`, same generated
  `env`/`access`, i.e. the same credentials/flags — and mark `stopped=True`.
  Deliberately does **not** release published ports, so a resumed instance
  keeps the exact `connect_host:connect_port` a learner may already have.
  `pause_range()` also deliberately leaves the range's shared overlay network
  in place (targets are paused/resumed independently).
- `InstanceController._resume_record()` / `_resume_range_if_stopped()`:
  recreate the Docker resources straight from the persisted plan (no
  replanning, no new `secrets.token_urlsafe()` call) and clear `stopped`.
  Wired into:
  - `create_or_get()`'s existing-record branch (an ordinary reopen resumes a
    paused instance/range transparently).
  - `reboot()` / `reboot_range_attacker()` (a reboot against a paused
    instance now resumes it instead of a no-op `force_update()` against a
    service that no longer exists).
- `reaper.py`: `_sweep_idle_instances`, `_sweep_due_shutdowns`, and
  `_sweep_idle_ranges` now call `pause()`/`pause_range()` instead of
  `teardown()`/`teardown_range()`. `_sweep_expired_instances` /
  `_sweep_expired_ranges` (the **absolute lifetime ceiling**) are unchanged —
  that's a genuine, one-way expiration and still deletes the row (and
  therefore the credentials) for real, even for an already-paused
  record — see `test_sweep_absolute_lifetime_also_destroys_an_already_paused_instance`.
  This is the one place credentials are allowed to stop being valid without
  an explicit relaunch, and it's intentional (session ceiling).
- `create_or_get(force_relaunch=True)` (explicit relaunch/reset) is
  unchanged: it always replans from scratch, so it's still the only
  in-session path that rotates credentials — confirmed by
  `test_relaunch_after_pause_does_rotate_credentials`.

### API-visible signaling

- `POST /instances` now returns `status="resumed"` (200) when it recreated a
  previously-paused instance, distinct from `"exists"` (200, was already
  running) and `"created"` (201, fresh credentials — first launch or an
  explicit `relaunch: true`). `main.py`'s `create_instance()` route.
- `POST /instances/<o>/<k>/reboot` and `POST /ranges/<o>/attacker/reboot`
  return `status="resumed"` instead of `"rebooting"` when the target was
  paused.
- `GET /instances/<o>/<k>` (and `/admin/instances`, `/admin/ranges`) now
  include a `stopped` boolean, plus (on the non-admin route) `idle_pause_at`
  (when the next idle sweep will pause it, if currently live) and
  `expires_at` (when the absolute lifetime ceiling will delete it for real,
  if `MAX_INSTANCE_LIFETIME_MINUTES` is configured) — a countdown/warning
  surface for the CTFd-side UI, per the task's "surface a countdown before
  automatic cleanup" ask. `expires_at` is the one deadline that actually
  ends credential validity; `idle_pause_at` does not.

### Expiration behavior (documented, as requested)

- **Idle pause** (`IDLE_GRACE_MINUTES`, default 120) and **post-solve
  shutdown** (`schedule-shutdown`/`extend-shutdown`): non-destructive.
  Credentials/flags survive; the environment resumes identically on the next
  touch/reboot. No caller-visible warning is currently sent before this
  fires (it's reversible, so lower urgency) — `idle_pause_at` in the
  instance response is the mechanism available for CTFd to poll/display a
  countdown if desired; wiring that into the CTFd-side UI is out of this
  fix's scope (owned by other in-flight instance-launcher work).
  Instance's `expires_at` — see `expires_at` above.
- **Reboot** (`/reboot`): in-place restart if live, resume-from-plan if
  paused. Never destructive.
- **Absolute lifetime ceiling** (`MAX_INSTANCE_LIFETIME_MINUTES`, default
  240): destructive, one-way, independent of activity/pauses. This is the
  only automatic path where credentials genuinely stop being valid.
  `expires_at` in the instance response is the countdown surface for this.
- **Explicit relaunch** (`relaunch: true`) / **explicit delete**
  (`DELETE /instances/...`, `DELETE /ranges/...`): destructive by design,
  always rotates credentials on relaunch. Unchanged by this fix.

### The documented signing contract (Wargames side, already designed)

From `hint-wallet-sync-deployment.md` + `deploy.sh:sync_hint_wallet_bundle()`:

- **Secret**: env var `HINT_WALLET_SYNC_SECRET` on the Wargames deploy job
  side must exactly match a Docker secret mounted at
  `/run/secrets/hint_wallet_sync_secret` on the Engine side. High-entropy,
  >=32 chars enforced by `deploy.sh` (`${#secret} -ge 32`). Provisioned via
  `openssl rand -base64 48 | docker secret create hint_wallet_sync_secret -`.
  This is a **new, dedicated secret** — explicitly distinct from any
  participant/challenge secret and (per my check above) distinct from
  `plugin_shared_secret`.
- **Signature**: HMAC-SHA256 over the raw JSON bundle bytes, hex digest,
  using that secret as the HMAC key (`hmac.new(secret.encode(), raw,
  hashlib.sha256).hexdigest()` in `deploy.sh`).
- **Payload**: one JSON bundle, `{"schema_version": 1, "revision": <int>,
  "manifests": [...]}`, always containing all three tracks (Bandit,
  Krypton, Natas) together — Engine must validate signature, revision,
  schema, all three track counts, tier costs, and cross-track references,
  then commit all three in a single DB transaction. It must never leave a
  one- or two-track catalog active.
- **Revision semantics**: `HINT_WALLET_REVISION` must be a positive integer,
  strictly increasing. Engine accepts a revision higher than the last
  accepted one; accepts an exact retry of the *same* revision only if the
  signed catalog digest is byte-identical (idempotent retry); rejects a
  lower revision outright; rejects a same-revision/different-digest payload
  (`409 revision_digest_conflict`). No rollback via revision — corrections
  ship as a new higher revision.
- **Required fail-closed HTTP responses**: `401 invalid_signature`,
  `400 invalid_schema`, `400 incomplete_tracks`, `409 stale_revision`,
  `409 revision_digest_conflict`, `422 catalog_validation_failed`,
  `503 secret_or_database_unavailable`. On any of these, the previously
  accepted three-track catalog must remain active untouched.
- **Rotation**: Engine must be able to accept old-and-new secret IDs
  simultaneously during a short overlap window (so this isn't a bare
  single-value secret compare — it implies a small keyed-secret-by-ID
  lookup, not just one env var).
- **Transport**: internal HTTPS only, hostname + cert validation enabled,
  no insecure-TLS override. Audit logging must record secret IDs, revision,
  catalog digest, operator, timestamp, result — **never** the secret,
  signature, or payload body.

(`sudo docker secret ls`) and as
`/opt/cei-labs/cei-labs-engine/docker/secrets/hint_wallet_sync_secret.txt`

### What was built

- **`app/config.py`**: `HINT_WALLET_SYNC_SECRET` (from the
  `hint_wallet_sync_secret` Docker secret / env var fallback, matching the
  existing `_read_secret` pattern) and `HINT_WALLET_SYNC_SECRET_PREVIOUS`
  (from an optional `hint_wallet_sync_secret_previous` secret, present only
  during a coordinated rotation window).

- **`app/wallet.py`** (new module): pure validation, no HTTP/DB
  dependencies, so it's directly unit-testable.
  - `validate_bundle(bundle) -> manifests`: full structural/type schema
    check (exact top-level and per-object key sets, types, positive
    integers, non-empty strings) raising `WalletSchemaError`; track
    completeness (exactly bandit+krypton+natas, once each) raising
    `WalletIncompleteTracksError`; then per-manifest tamper check (recomputed
    digest over `{schema_version,track,entries}` must match the manifest's
    claimed `digest`, replicating deploy.sh's signing script exactly) and
    per-entry economic check (tiers numbered 1,2,3; costs strictly
    increasing) raising `WalletValidationError`.
  - `manifest_digest()`, `find_hint_cost()`, `find_hint_content()` — the
    last two look up a specific tier's price/text out of an already-accepted
    catalog's manifest list.

- **`app/store.py`**: new `WalletStore` class (same file/pattern as
  `InstanceStore`/`RangeStore`, sharing `STORE_DB_PATH` — already how the
  three existing stores coexist in one SQLite file).
  - `wallet_catalog` (singleton row: revision, digest, bundle_json,
    secret_id, accepted_at).
  - `team_balance` (owner_id -> integer balance).
  - `wallet_unlocks` (owner_id, track, entry_name, tier, cost, unlocked_at
    — primary key makes a repeated unlock a no-op read instead of a second
    charge).
  - `try_accept_catalog(revision, digest, manifests, secret_id)`: the
    revision/digest state machine from the deployment doc, entirely inside
    one `BEGIN IMMEDIATE` transaction (same race the existing
    `InstanceStore.reserve()` closes, applied here to catalog syncs):
    returns `"accepted"` (no catalog yet, or strictly higher revision),
    `"idempotent"` (same revision, same digest — no-op, no write),
    `"conflict"` (same revision, different digest), or `"stale"` (lower
    revision). A rejected sync performs no write at all, so the previously
    accepted three-track catalog is guaranteed untouched.
  - `unlock_hint(owner_id, track, entry_name, tier, cost)`: also one
    `BEGIN IMMEDIATE` transaction — check-already-unlocked, check-balance,
    and spend all happen atomically, closing the same double-spend race
    class as `InstanceStore.reserve()`.

- **`app/main.py`**:
  - `POST /wallet/sync` — the one route exempted from the standard
    `X-Orchestrator-Auth` check in `before_request` (different trust
    boundary: the Wargames release pipeline, not the CTFd plugin). Verifies
    `X-Hint-Wallet-Signature` as HMAC-SHA256 over the *raw* request bytes
    against every currently-configured secret (current, and previous during
    rotation) using `hmac.compare_digest`; on match, runs schema ->
    track-completeness -> economic validation via `app.wallet`, computes
    `sha256(raw_body)` as the catalog digest, and calls
    `WalletStore.try_accept_catalog`. Maps outcomes to exactly the
    documented codes: `401 invalid_signature`, `400 invalid_schema`,
    `400 incomplete_tracks`, `422 catalog_validation_failed`,
    `409 stale_revision`, `409 revision_digest_conflict`,
    `503 secret_or_database_unavailable` (no secret configured, or a DB
    exception), `200` on accept/idempotent. Audit-logs secret_id, revision,
    digest, result, timestamp — never the secret, signature, or payload body
    (per the deployment doc's explicit instruction).
  - `POST /wallet/deduct`, `GET /wallet/balance/<owner_id>`,
    `POST /wallet/credit` — the CTFd-plugin-facing hooks sketched in the
    "next steps" section above, authenticated the normal
    `X-Orchestrator-Auth` way like `/instances*`. `deduct` is idempotent on
    retry (`already_unlocked` status, no re-charge) and returns
    `402 insufficient_balance` when the team can't afford the tier,
    `404 hint_not_found` for an unknown track/entry/tier, and
    `409 no_active_catalog` if no bundle has ever been synced.

- **`docker/stack.yml`**: added the `hint_wallet_sync_secret` (file-sourced,
  same convention as `plugin_shared_secret`) to the top-level `secrets:`
  block and to the `orchestrator` service's mounted secrets list, so it's
  actually available at `/run/secrets/hint_wallet_sync_secret` in
  production. `hint_wallet_sync_secret_previous` was deliberately *not*
  added — it only gets provisioned (and added to `docker/secrets/` +
  `stack.yml`) at actual rotation time, per the deployment doc's
  "Coordinated rotation" section; `config.py`'s `_read_secret` already
  degrades gracefully to `""` (ignored) when that file doesn't exist.
