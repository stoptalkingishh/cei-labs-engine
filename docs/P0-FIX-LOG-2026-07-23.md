# P0 Fix Log — Credential Encryption at Rest (2026-07-23)

**Branch:** `fix/p0-credential-encryption` · **Base:** `8308661` (`main`)

## What this fixes

`InstanceStore`/`RangeStore` (`docker/orchestrator/app/store.py`) persist
each instance/range's full `plan_json` to a SQLite file on the
`orchestrator_data` volume so a restart doesn't lose track of live Docker
resources. That `plan_json` embeds every credential the orchestrator ever
generates — VNC/SSH passwords (`instance_types.py`'s
`plan_web_app`/`plan_single_target`/`plan_range_attacker`) and, since the
per-team dynamic-flag work landed, each team's actual flag answer riding
the `access` dict until `routes.py`'s `_persist_and_scrub_secrets` extracts
it CTFd-side. Before this fix, all of that sat in plaintext in a SQLite
file on disk with no encryption at rest — anyone with read access to the
`orchestrator_data` volume (a host compromise, a misconfigured backup, a
stray `docker cp`) could read every team's live VM passwords and flags.

## Starting point: what a previous run had already built

A prior session on this branch crashed mid-work on a usage-limit error but
left real, largely-correct progress uncommitted. I reviewed it file-by-file
before continuing (see commit for the full diff):

- **`docker/orchestrator/app/crypto.py`** (new) — `CredentialCipher`, a thin
  wrapper around `cryptography.fernet.Fernet` (AES-128-CBC + HMAC-SHA256,
  authenticated). `from_key_material()` reads the key from the
  `credential_encryption_key` Docker secret and falls back to a loudly-logged
  ephemeral random key if unset/invalid, so every environment still gets
  real encryption even when misconfigured (persisted credentials just won't
  survive a restart in that case).
- **`docker/orchestrator/app/store.py`** — `_encrypt_plan`/`_decrypt_plan`
  wrap every read/write of the `plan_json` column. `_decrypt_plan` falls
  back to treating a value as already-plaintext JSON if it's not a valid
  Fernet token, so pre-upgrade rows keep working and self-upgrade to
  ciphertext the next time they're written.
- **`docker/orchestrator/app/config.py`** — new `CREDENTIAL_ENCRYPTION_KEY`
  config value, read the same way every other secret in this file is.
- **`docker/orchestrator/app/main.py`** — `create_app` builds one
  `CredentialCipher` and shares it between `InstanceStore` and `RangeStore`.
- **`docker/stack.yml`** — new `credential_encryption_key` secret, mounted
  into the `orchestrator` service (and `ctfd`, though CTFd doesn't currently
  read it — harmless, matches this file's existing pattern of mounting
  secrets a service might need).
- **`docker/orchestrator/requirements.txt`** — added `cryptography==45.0.6`.
- **`scripts/install.sh`** / **`scripts/offline-install.sh`** — generate a
  real Fernet key (not an arbitrary alnum string like the other secrets)
  for `credential_encryption_key.txt` if missing/still a placeholder.
- **`docker/secrets.example/credential_encryption_key.txt`** (new) — a
  `CHANGE_ME_...` placeholder documenting the exact command to generate a
  real key, matching every other file in `secrets.example/`.

This design is sound and I kept it. The key is read from a mounted Docker
secret file (`docker/secrets/credential_encryption_key.txt`, gitignored),
never hardcoded and never stored in the same SQLite file as the ciphertext
it protects — matching this repo's existing `docker/secrets`/
`docker/secrets.example` pattern for every other credential.

## What I found and fixed while completing it

**Bug: encryption broke the existing multi-worker concurrency guarantee.**
Running the full existing suite surfaced two real failures, not present on
`main`:

- `tests/test_controller.py::test_parallel_relaunches_converge_on_one_replacement`
- `tests/test_store_concurrency.py::test_relaunch_claim_is_atomic_across_independent_store_objects`

Root cause: both tests construct several independent `InstanceStore`/
`RangeStore` objects (standing in for separate gunicorn worker processes)
against the same on-disk SQLite file, without passing a `cipher=`. Each one
defaulted to `CredentialCipher.from_key_material(None)` — a **fresh random
ephemeral key per store**. So "worker A" encrypted a plan under key A and
"worker B" tried to decrypt it under key B, hit `InvalidToken`, and (per
`_decrypt_plan`'s legacy-row fallback) returned the raw ciphertext to
`json.loads()`, which threw.

This is a real deployment property, not just a test artifact: real
gunicorn workers are separate OS processes that each independently call
`create_app()`, but they all read the *same* mounted
`credential_encryption_key` secret file, so `from_key_material(same_string)`
gives every worker a functionally identical cipher in production. The two
tests just hadn't been updated to reflect that a shared secret file means a
shared (deterministic) key. Fixed by having each "worker" store in both
tests share one explicit `CredentialCipher` (mirroring "same secret file on
disk"), not by changing any production code path — see the diff on
`docker/orchestrator/tests/test_controller.py` and
`docker/orchestrator/tests/test_store_concurrency.py`.

No other issues found in the inherited WIP.

## Audit against the four checklist items

1. **Credential encryption at rest** — done (inherited WIP, verified + the

   detection via `InvalidToken`, cross-key isolation, ephemeral-fallback
   behavior) and `test_store_encryption.py` (raw SQLite bytes never contain

   under the wrong key doesn't leak, pre-upgrade plaintext rows still read).

2. **Audit API responses for credential/answer leakage** —
   `docker/ctfd/plugins/instance-launcher/routes.py`'s
   `_persist_and_scrub_secrets` already extracts every per-team flag value
   out of the orchestrator's `access` dict and into `TeamChallengeSecret`
   *before* any status dict reaches a template or JSON response
   (`_fetch_and_scrub_status` is the only path either route uses to fetch
   status). This is pre-existing, unmodified code — I read it, confirmed
   both `/api/status/<id>` and `/api/launch/<id>` call it, and added
   `docker/ctfd/plugins/instance-launcher/tests/test_secret_scrubbing.py`
   (6 new tests) to lock the behavior in: a flag value is removed from
   `access` before it could reach a player, ordinary connect info (URL,
   VNC/SSH password — which the player IS meant to see, that's their
   environment access) survives untouched, and instance-group siblings
   (a shared boot2root box) all get scrubbed from one shared response.
   Ordinary VM connect credentials (VNC/SSH password) are intentionally
   returned to the owning player — that's the product, not a leak; only
   flag/answer values are the leakage risk this addresses.

3. **Post-solve session issuance, rate-limiting, CSRF, IDOR** — audited,
   not modified (already handled by the existing, pre-P0 architecture; see
   "Not addressed" below for what I could NOT verify with an executable
   test):
   - **CSRF**: `/api/launch/<id>` and `/launch/<id>` are `@authed_only` with
     no `@bypass_csrf_protection`, so CTFd's own global CSRF check applies.
     The one route that does bypass it (`/admin/mappings/sync`) is
     deliberately headless-only and gates on `hmac.compare_digest` against
     the `plugin_shared_secret` Docker secret instead.
   - **Rate-limiting**: Traefik middleware in `docker/stack.yml` already
     rate-limits the CTFd flag-attempt endpoint specifically
     (`ctfd-attempt-ratelimit`: 2 req/s average, burst 5) plus a general
     50 req/s/burst 100 limit on all of CTFd.
   - **IDOR**: every route in `routes.py` derives `owner_id` from
     `get_current_user().account_id` (the CTFd session), never from a URL
     or body parameter — so there is no parameter a player can tamper with
     to read another team's data. `TeamChallengeSecret` is keyed
     `(owner_id, challenge_id)` with a matching `UniqueConstraint`. The
     orchestrator's own `/instances/<owner_id>/<instance_key>` API *does*
     take `owner_id` as a path parameter, but it's on
     `orchestrator-internal`, a Swarm overlay network declared
     `internal: true` in `docker/stack.yml` and joined by nothing but
     `ctfd`/`orchestrator` — confirmed no challenge/edge/participant-facing
     service is attached to it, so it's unreachable from a player
     regardless of parameter tampering. `test_secret_scrubbing.py`'s
     `test_two_teams_sharing_a_challenge_never_collide_or_cross_leak`
     exercises the (owner_id, challenge_id)-keying property directly.
   - **Session issuance**: CTFd's own login session (not something this
     plugin or the orchestrator issues) is what gates every route here;
     this plugin never mints its own token from a raw answer/credential —
     `PerTeamDynamicFlag.compare()` (`flags.py`) validates a submission by
     `hmac.compare_digest` against the stored value and returns a bool to
     CTFd's own solve flow, nothing plugin-issued rides back to the player.

## Follow-up (same day): fail closed on a missing/invalid production key

**Code review finding:** `CredentialCipher.from_key_material()`
(`docker/orchestrator/app/crypto.py`) silently falls back to a fresh
ephemeral in-process key (just a logged warning) whenever
`credential_encryption_key` is unset, blank, or invalid — it never fails
closed. Every other secret-gated thing in this codebase fails loudly
instead: `operator/kali-novnc/Dockerfile`'s `/start.sh` `exit 1`'s without
`VNC_PASSWORD`/`OPERATOR_PASSWORD`; `POST /wallet/sync` (PR #13) 503s
without `hint_wallet_sync_secret`. Concretely: if a real deployment forgets
to set `credential_encryption_key` (or loses it across a restart without
persisting it), the orchestrator would silently start anyway with a new
random key each time — and per `store.py`'s own
`test_a_row_written_under_one_key_is_unreadable_under_a_different_key`,
reading data encrypted under a different key than currently configured
*raises*, not degrades gracefully. So this isn't just "credentials become
unreadable" — it's a delayed, confusing crash on `store.get()`/
`store.all()` on the *next* restart (including the reaper's every-sweep
`store.all()` call), instead of a loud, immediate deploy-time failure.

**What changed:**

- **`docker/orchestrator/app/crypto.py`** — extracted the "is this a
  usable, non-blank Fernet key?" check `from_key_material()` already made
  internally into a standalone `is_valid_key_material()` function (same
  logic, no behavior change to `from_key_material()` itself — it still
  falls back to an ephemeral key exactly as before, which
  `test_from_key_material_falls_back_to_a_working_ephemeral_key_rather_than_raising`
  and `test_pre_encryption_plaintext_row_is_still_readable_after_upgrade`
  (via `InstanceStore(db_path=db_path)` with no `cipher=`) rely on, and
  which is genuinely useful for local dev/test convenience).
- **`docker/orchestrator/app/main.py`** — `create_app()` now raises
  `RuntimeError` and refuses to build the app when it's running the
  production path (see below) and
  `is_valid_key_material(cfg.CREDENTIAL_ENCRYPTION_KEY)` is false, *before*
  constructing the Docker client, cipher, or stores.

**How "production" is detected without new config surface:** every call
site in this repo already distinguishes itself along exactly this line —
`app/wsgi.py` (the real gunicorn entrypoint) calls `create_app()` with no
arguments at all, defaulting `cfg` to a real `Config()` that reads from
env/Docker secrets; every test (`tests/test_api.py`'s `client` fixture,
`test_auth_rejected_when_no_secret_configured`, etc.) constructs and passes
its own `FakeConfig` explicitly. `config is None` is that existing
distinction, not a new one — no new `Config` field, no `TESTING`/`DEBUG`
flag introduced. The gate only fires on the true no-config production path,
so `CredentialCipher.from_key_material()`'s dev/test-friendly ephemeral
fallback keeps working unchanged for every existing caller that passes a
config explicitly.

**New tests** (`docker/orchestrator/tests/test_api.py`):
- `test_create_app_refuses_to_start_in_production_without_a_credential_encryption_key`
- `test_create_app_refuses_to_start_in_production_with_an_invalid_credential_encryption_key`
- `test_create_app_starts_fine_in_production_with_a_valid_credential_encryption_key`
- `test_create_app_with_an_explicit_config_is_never_subject_to_the_production_gate`

These patch `Config.CREDENTIAL_ENCRYPTION_KEY` directly with
`monkeypatch.setattr` rather than the `CREDENTIAL_ENCRYPTION_KEY` env var —
`Config`'s attributes (like every value in that file) are computed once at
class-definition/import time via `_read_secret`, so setting the env var
from inside a test after import has no effect on an already-imported
`Config` class; patching the class attribute is the accurate way to
simulate "this deployment does/doesn't have the secret mounted."

# P0 fix log: VNC/SSH attacker-workstation password truncation

## 2026-07-23 -- fix/p0-vnc-ssh-password

### The bug

`plan_range_attacker()` in `docker/orchestrator/app/instance_types.py`
generated ONE `secrets.token_urlsafe(18)` string (20+ characters) and set
both `VNC_PASSWORD` and `OPERATOR_PASSWORD` to that same value. The
attacker workstation's launch panel then surfaced a single
`attacker_password` field, presented as "the" password for both SSH and
noVNC.

TigerVNC's protocol silently truncates its password to 8 characters --
`vncpasswd -f` does not warn or error, it just discards everything past
the 8th byte. So SSH (via `chpasswd`, no length limit) honored the full
generated string, while VNC only ever actually accepted its first 8
characters. Whatever the UI displayed as "the" password would silently
fail to authenticate over noVNC unless a player happened to truncate it
themselves.

Separately, on inspection `operator/kali-novnc/Dockerfile`'s embedded
`/start.sh` turned out to not even reference `OPERATOR_PASSWORD` at all --
it read `VNC_PASSWORD` for *both* `chpasswd` (the Linux/SSH account) and
`vncpasswd -f` (VNC auth). `OPERATOR_PASSWORD` was dead weight for this
image (it's meaningful only for `operator/analyst/Dockerfile`, the
SSH-only variant with no VNC server at all). So the two orchestrator env
vars were not actually independent inputs into two different mechanisms
for kali-novnc -- both were driven off one value under the hood too.

### The fix

1. **`docker/orchestrator/app/instance_types.py`** (`plan_range_attacker`):
   generate two genuinely separate values --
   - `ssh_password = secrets.token_urlsafe(18)` (unchanged, long/high-entropy, no truncation ceiling to worry about for SSH/chpasswd)
   - `novnc_password` = a fresh 8-character alphanumeric string (`secrets.choice` over `string.ascii_letters + string.digits`), generated at exactly the length TigerVNC actually honors so there is no truncation gap between what's generated and what's usable.
   - `attacker_env["OPERATOR_PASSWORD"] = ssh_password`, `attacker_env["VNC_PASSWORD"] = novnc_password`.
   - `access` dict: replaced the single `attacker_password` key with two clearly labeled fields, `ssh_password` and `novnc_password`. No shared/merged `password` field remains anywhere in the response.

2. **`operator/kali-novnc/Dockerfile`** (`/start.sh`, generated inline):
   - now checks both `OPERATOR_PASSWORD` and `VNC_PASSWORD` are set at container start (fails loudly, refuses to start with no password, same as before -- just for both vars now).
   - `chpasswd` now uses `OPERATOR_PASSWORD` (was `VNC_PASSWORD`).
   - `vncpasswd -f` continues to use `VNC_PASSWORD` (unchanged target, now genuinely a different value than what drives SSH).
   - Updated the Dockerfile-level comments (the "VNC_PASSWORD is intentionally not an ARG" block, the "same account, same password" line, the `/start.sh` comment) to describe the two-credential model instead of implying a single shared secret.

3. **Launch-panel surfaces** -- grepped `docker/orchestrator/app/` and the CTFd instance-launcher plugin broadly for `attacker_password` / `VNC_PASSWORD` / `OPERATOR_PASSWORD`; the only two places that rendered the old shared field to end users were:
   - `docker/ctfd/plugins/instance-launcher/assets/challenge-launch.js` (the in-modal JS panel)
   - `docker/ctfd/plugins/instance-launcher/templates/instance_launcher/launch.html` (the no-JS fallback page)

   Both now render three distinct lines -- Username, "SSH / console password", "noVNC password" -- instead of one combined "Login: user / password" line captioned "needed for both noVNC and SSH" (which was actively misleading given the bug above).

   `operator/analyst/Dockerfile` (the SSH-only, no-VNC image) was already correctly using only `OPERATOR_PASSWORD` and needed no change -- confirmed by reading it, not assumed.

## Bug

`VNC_PASSWORD`/`OPERATOR_PASSWORD` (and single-target/wargame level flags baked
into `env`) were generated fresh — via `instance_types.plan_*()`, which calls
`secrets.token_urlsafe()`/`generate_track_secrets()` — every time a *new*
`InstanceRecord`/`RangeRecord` row was created. That's correct for an actual
first launch or an explicit relaunch. The bug: the idle reaper and the
post-solve shutdown countdown both went through `InstanceController.teardown()`/
`teardown_range()` — the same *destructive* path used for an explicit delete —
which deletes the store row entirely. The next time a learner reopened the
challenge (an ordinary, non-`relaunch` `POST /instances` call), `create_or_get()`
found no existing row, replanned from scratch, and silently handed back a
*new* set of credentials under the same `status="exists"`-shaped response the
learner had no reason to distrust.

Docker/Swarm-level restarts (host reboot recreating a task, `force_update()`
in `reboot()`) were never actually the bug — a service's env is part of its
task spec and survives those untouched. The real gap was idle/shutdown-driven
*teardown*, not restart.

## Fix

Introduced a non-destructive "pause" state, orthogonal to teardown:

- `InstanceRecord.stopped` / `RangeRecord.stopped` (new `stopped` column,
  `docker/orchestrator/app/store.py`, migrated onto the existing on-disk db
  via `ALTER TABLE ... ADD COLUMN` guarded against "duplicate column").
- `InstanceController.pause()` / `pause_range()` (`controller.py`): remove the
  live Docker service(s) (and, for a single/web-app instance, its own
  network) but **keep the store row** — same `plan`, same generated
  `env`/`access`, i.e. the same credentials/flags — and mark `stopped=True`.
  Deliberately does **not** release published ports, so a resumed instance
  keeps the exact `connect_host:connect_port` a learner may already have.
  `pause_range()` also deliberately leaves the range's shared overlay network
  in place (targets are paused/resumed independently).
- `InstanceController._resume_record()` / `_resume_range_if_stopped()`:
  recreate the Docker resources straight from the persisted plan (no
  replanning, no new `secrets.token_urlsafe()` call) and clear `stopped`.
  Wired into:
  - `create_or_get()`'s existing-record branch (an ordinary reopen resumes a
    paused instance/range transparently).
  - `reboot()` / `reboot_range_attacker()` (a reboot against a paused
    instance now resumes it instead of a no-op `force_update()` against a
    service that no longer exists).
- `reaper.py`: `_sweep_idle_instances`, `_sweep_due_shutdowns`, and
  `_sweep_idle_ranges` now call `pause()`/`pause_range()` instead of
  `teardown()`/`teardown_range()`. `_sweep_expired_instances` /
  `_sweep_expired_ranges` (the **absolute lifetime ceiling**) are unchanged —
  that's a genuine, one-way expiration and still deletes the row (and
  therefore the credentials) for real, even for an already-paused
  record — see `test_sweep_absolute_lifetime_also_destroys_an_already_paused_instance`.
  This is the one place credentials are allowed to stop being valid without
  an explicit relaunch, and it's intentional (session ceiling).
- `create_or_get(force_relaunch=True)` (explicit relaunch/reset) is
  unchanged: it always replans from scratch, so it's still the only
  in-session path that rotates credentials — confirmed by
  `test_relaunch_after_pause_does_rotate_credentials`.

### API-visible signaling

- `POST /instances` now returns `status="resumed"` (200) when it recreated a
  previously-paused instance, distinct from `"exists"` (200, was already
  running) and `"created"` (201, fresh credentials — first launch or an
  explicit `relaunch: true`). `main.py`'s `create_instance()` route.
- `POST /instances/<o>/<k>/reboot` and `POST /ranges/<o>/attacker/reboot`
  return `status="resumed"` instead of `"rebooting"` when the target was
  paused.
- `GET /instances/<o>/<k>` (and `/admin/instances`, `/admin/ranges`) now
  include a `stopped` boolean, plus (on the non-admin route) `idle_pause_at`
  (when the next idle sweep will pause it, if currently live) and
  `expires_at` (when the absolute lifetime ceiling will delete it for real,
  if `MAX_INSTANCE_LIFETIME_MINUTES` is configured) — a countdown/warning
  surface for the CTFd-side UI, per the task's "surface a countdown before
  automatic cleanup" ask. `expires_at` is the one deadline that actually
  ends credential validity; `idle_pause_at` does not.

### Expiration behavior (documented, as requested)

- **Idle pause** (`IDLE_GRACE_MINUTES`, default 120) and **post-solve
  shutdown** (`schedule-shutdown`/`extend-shutdown`): non-destructive.
  Credentials/flags survive; the environment resumes identically on the next
  touch/reboot. No caller-visible warning is currently sent before this
  fires (it's reversible, so lower urgency) — `idle_pause_at` in the
  instance response is the mechanism available for CTFd to poll/display a
  countdown if desired; wiring that into the CTFd-side UI is out of this
  fix's scope (owned by other in-flight instance-launcher work).
  Instance's `expires_at` — see `expires_at` above.
- **Reboot** (`/reboot`): in-place restart if live, resume-from-plan if
  paused. Never destructive.
- **Absolute lifetime ceiling** (`MAX_INSTANCE_LIFETIME_MINUTES`, default
  240): destructive, one-way, independent of activity/pauses. This is the
  only automatic path where credentials genuinely stop being valid.
  `expires_at` in the instance response is the countdown surface for this.
- **Explicit relaunch** (`relaunch: true`) / **explicit delete**
  (`DELETE /instances/...`, `DELETE /ranges/...`): destructive by design,
  always rotates credentials on relaunch. Unchanged by this fix.

## Not touched (explicitly out of scope)

VNC/SSH credential *generation* itself (`secrets.token_urlsafe()` calls in
`instance_types.py`), encryption-at-rest of stored credentials, the
hint-wallet endpoint, and content deployment — separate P0 fixes own those

### The documented signing contract (Wargames side, already designed)

From `hint-wallet-sync-deployment.md` + `deploy.sh:sync_hint_wallet_bundle()`:

- **Secret**: env var `HINT_WALLET_SYNC_SECRET` on the Wargames deploy job
  side must exactly match a Docker secret mounted at
  `/run/secrets/hint_wallet_sync_secret` on the Engine side. High-entropy,
  >=32 chars enforced by `deploy.sh` (`${#secret} -ge 32`). Provisioned via
  `openssl rand -base64 48 | docker secret create hint_wallet_sync_secret -`.
  This is a **new, dedicated secret** — explicitly distinct from any
  participant/challenge secret and (per my check above) distinct from
  `plugin_shared_secret`.
- **Signature**: HMAC-SHA256 over the raw JSON bundle bytes, hex digest,
  using that secret as the HMAC key (`hmac.new(secret.encode(), raw,
  hashlib.sha256).hexdigest()` in `deploy.sh`).
- **Payload**: one JSON bundle, `{"schema_version": 1, "revision": <int>,
  "manifests": [...]}`, always containing all three tracks (Bandit,
  Krypton, Natas) together — Engine must validate signature, revision,
  schema, all three track counts, tier costs, and cross-track references,
  then commit all three in a single DB transaction. It must never leave a
  one- or two-track catalog active.
- **Revision semantics**: `HINT_WALLET_REVISION` must be a positive integer,
  strictly increasing. Engine accepts a revision higher than the last
  accepted one; accepts an exact retry of the *same* revision only if the
  signed catalog digest is byte-identical (idempotent retry); rejects a
  lower revision outright; rejects a same-revision/different-digest payload
  (`409 revision_digest_conflict`). No rollback via revision — corrections
  ship as a new higher revision.
- **Required fail-closed HTTP responses**: `401 invalid_signature`,
  `400 invalid_schema`, `400 incomplete_tracks`, `409 stale_revision`,
  `409 revision_digest_conflict`, `422 catalog_validation_failed`,
  `503 secret_or_database_unavailable`. On any of these, the previously
  accepted three-track catalog must remain active untouched.
- **Rotation**: Engine must be able to accept old-and-new secret IDs
  simultaneously during a short overlap window (so this isn't a bare
  single-value secret compare — it implies a small keyed-secret-by-ID
  lookup, not just one env var).
- **Transport**: internal HTTPS only, hostname + cert validation enabled,
  no insecure-TLS override. Audit logging must record secret IDs, revision,
  catalog digest, operator, timestamp, result — **never** the secret,
  signature, or payload body.

## 2026-07-23 — CTFd-side plugin for the hint-wallet sync gap

### Summary

### What was built

- **`orchestrator_client.py`** — copied instance-launcher's client
  conventions exactly: `ORCHESTRATOR_URL` env var (default
  `http://orchestrator:8080` — the Swarm overlay service DNS name/port,

  `read_secret()`, `X-Orchestrator-Auth` header. Adds

  anyway — otherwise proxies the raw body/header through unchanged and
  relays whatever status/body comes back. On a `200` from the orchestrator
  only, best-effort caches the bundle locally (see below); a caching
  failure is logged and never surfaces to the sync caller, since the
  orchestrator's acceptance is the real outcome.

  instance-launcher usage and hint-wallet balance key identically.
  `api_unlock` calls `deduct()` and returns its exact status code

  200.

  consumers, so a hint's text still only comes from a real `deduct()` call.

  `HintWalletCatalog`'s table with `checkfirst=True`, same pattern as
  `instance-launcher/__init__.py`.
